**17 readers, 75 graded questions, three arms.** Read #5's instrument

three new questions that cannot be answered without calling `fetch`.

|---|---:|---:|

| compressed | **75/75** | 71/72 |

**The stored arm's own verdict is FAIL** — `GRADED_ALLOWED_GAP = 0` and the gap is

here, because a bar set in advance is only worth having if it is reported when it
is missed (`src/eval_model.py`, *the bar, written before the first run*).

## What it settles: `_key`

**C8 — "give the complete record for ethereum" — is correct in all three arms.**
Read #5's only compressed miss is gone, and cold read #6 the same day says why in
the reader's own words: the legend clause decided a call the reader still
describes as a judgment call.

Two readers, two instruments, one fix. The compressed arm is now **75/75** — the
first perfect compressed score in seven reads, on a question set three larger
than the one it last scored 71/72 on.

## What it settles: retrieval

Read #5's stated limitation was that the store was queried **exactly once**, on
`jsonplaceholder`, so "the store does not damage answers" rested on a single
fetch (`docs/cold-reads/2026-09-11.md`, *the retrieval gap*).

**This run fetched 4 times, across all three payloads that carry a store**, and
every retrieved answer was right:

| question | payload | what it required | stored arm |
|---|---|---|---|
| `Q14` issues whose body says it fixes #37507 | github | search across 30 handled bodies | **correct** |
| `Q15` repro URL inside #37534's body | github | one targeted body fetch | **correct** |
| `H14` first comment id of story 16582136 | hn | fetch a `dints` cell, then read its first value as absolute | **correct** |
| `J3` body of post 1 | jsonplaceholder | the one fetch read #5 had | **correct** |

`H14` is the one worth dwelling on. The stored cell comes back as
`16582146 6 3 2 3 2 …` — the raw delta encoding — and the reader had to fetch it,
then apply the `dints` legend clause to know the first token is absolute and the
rest are differences. It did, in one fetch. The legend earning its keep on a
value that was not even in the document is the strongest evidence so far that
these clauses are doing work.

Retrieval now has four observations instead of one, on three payloads instead of
one, including a non-prose value. **That is the gap `docs/store.md` named, closed.**

## What it did NOT settle: the same two misses, a second time

The stored arm missed `Q5` (issues with zero comments: said 10, truth 11) and
`Q6` (total comments: said 33, truth 31). **These are the same two questions read
#5's stored arm missed**, with a different reader on a different day.

Checked rather than assumed, again:

- `comments` decompresses **identically** in the compressed and stored arms —
  verified directly, 11 zeros and 31 total either way.
- **No `comments` cell is a handle.** The column the reader is counting is 30
  plain integers sitting in the document: `0,3,0,1,0,0,1,1,3,3,0,0,3,0,1,1,2,1,0,0,0,1,1,1,3,2,1,1,1,0`.
- The compressed arm answered both correctly from that same column, and so did
  raw.

So it is arithmetic, not the store — and this time the sharpest version of it:
**the same reader fetched two bodies out of the store correctly and then
miscounted thirty single-digit integers printed in front of it.** Retrieval is
not what is failing.

One sample became two. `docs/cold-reads.md` has said since read #3 that counting
is the format's standing weakness and that it has never been *demonstrated*
rather than suspected; two independent stored readers failing the same two
counting questions, with a control arm passing them both times, is closer to a
demonstration than anything before it.

**It is not fixed here, and it is not obvious what the fix is.** A count is not a
marker a legend can explain, and neither is a column of thirty numbers. The
honest statement is that the stored document is harder to count than the
compressed one for a reason nobody has isolated, and the run says FAIL until
somebody does.

## One method note, because it cost a wrong number

The first grade of this run reported **raw 74/75**, an `H14` miss the raw reader
had not made: the grader ran while the last answer file was still being written.
The file existed; it was not finished. The corrected run is the one at the top.

A file-count check is not a completion check — the same shape as Rule 2, one
level down: a gate that can silently observe an incomplete input reports a real
number about the wrong thing.
