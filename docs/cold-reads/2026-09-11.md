# Cold read #5 — 2026-09-11

**17 readers, 72 questions, three arms, scored against computed ground truth.**

## This is a different instrument from reads #1–#4, and the difference matters

Reads #1–#4 were one reader, asked to think aloud, flag what was ambiguous and
score its own confidence. This one is `src/eval_model.py --emit` / `--grade`: a
fresh reader per payload **and per arm**, each given a document and nothing else,
each answering the payload's own `ASK` questions into JSON, graded automatically
with `table.same_json` against ground truth computed from the raw payload.

What it gains: **a control arm.** For the first time the same questions were put
to the *uncompressed* payload too, so "the reader got it wrong" and "compression
cost the answer" are separable. Reads #1–#4 could never tell those apart.

What it loses: no confidence score, no "say bluntly what was ambiguous". Those
are the parts that found the defects in #1–#4. **This does not replace that read;
it measures a different thing.** Both are owed.

| | reads #1–#4 | this one |
|---|---|---|
| readers | 1 | 17 |
| arms | compressed only | raw / compressed / stored |
| grading | by hand | `same_json` vs computed truth |
| finds | ambiguity, hedging, confidence | answers that actually moved |

## The score

| arm | correct | |
|---|---:|---|
| raw (control) | **72/72** | the payload as fetched |
| compressed | **71/72** | 41.6% smaller |
| stored | **69/72** | 73.7% smaller |

Seven payload/arm pairs were not read at all, because they are byte-identical to
one that was: five payloads carry no `#store` line and two come back from the
compressor unchanged. Identical bytes cannot produce a different answer.

## What it found: `#keyed`'s `_key` reads as data

`C8` asks for the complete `ethereum` record. The reader returned all twelve
fields correctly — and a thirteenth, `_key`.

`_key` is the synthetic column `#keyed` uses to hold the key each record was
stored under. The legend says so: *"column `_key` holds each record's key"*. It
was not enough. Asked for "the complete record", the reader included the
scaffolding, because nothing in the document says `_key` is **not a field of the
record**.

Nothing is lost — `decompress` strips `_key`, and the round-trip gate has always
passed. This is a **legibility** defect, which is the only kind these reads exist
to find, and it is the first one found by a machine rather than by a person.

**Deliberately not fixed here.** A format legibility change owes a cold read and
a re-measure, and `docs/shapes.md` records twice what deciding off one
observation costs. The candidate fix is one clause in the legend.

## What it did not find, checked rather than assumed

The stored arm missed `Q5` (issues with zero comments: said 10, truth 11) and
`Q6` (total comments: said 32, truth 31). That looks like the store costing
answers. It is not:

- `comments` decompresses **identically** in the compressed and stored arms — 11
  zeros, 31 total, verified directly.
- No `comments` cell is a handle; only bodies and two titles were stashed.
- The compressed arm answered both correctly from the same column.

One reader, arithmetic, n=1. The counting weakness reads #1–#4 kept circling,
showing up again — this time with a control arm proving it was the reader.

## The retrieval gap, which is this read's real limitation

**The store was queried exactly once**, by the `jsonplaceholder` reader (all 100
bodies are stashed and `J3` asks for one). On `github_issues` and `hn_stories`
the store holds only bodies, and **no graded question reads a body** — the
questions that do are the 16 comprehension ones, which need a judge and were not
asked.

So this read confirms the store does not *damage* answers. It says almost nothing
about whether a reader retrieves *well*. That was read #4's subject, and read #4
had no store to actually call.

## One observation nobody asked for

The `hn_stories` **raw** reader had to pre-process its own task file: the payload
is a single ~40,000-token line, past the reading tool's limit, so it wrapped the
line before it could read it in two passes. It reported this unprompted.

The compressed document of the same payload is one line per record and needed no
such handling. That is not a measured claim about token counts — it is a claim
about *shape*, and it is the first time the format's line-per-record structure
has paid off for a reason other than size.

## Confidence

Not asked for, and its absence is the honest summary of this read: it can tell
you an answer moved, and it cannot tell you the reader was uneasy.
