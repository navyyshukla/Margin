# Cold read #6 — 2026-09-12

**One reader, `coingecko_prices` compressed, 10/10, confidence 9/10 — the highest
of the six.** Run to answer one question: does saying what `_key` is *not* stop a
reader reporting it as data?

It does, and the reader said why in its own words.

## Why this read exists

Cold read #5 (`docs/cold-reads/2026-09-11.md`) asked C8 — "give the complete
record for ethereum" — and got all twelve fields plus a thirteenth, `_key`. The
legend at the time said:

```
#keyed = rows came from an object; column _key holds each record's key
```

True, and not enough: it said what the column *is* and left "…and therefore is
not one of the record's own fields" to be inferred. The fix is one clause, and
this is the read it owes (`harness` skill, *Before adding a format element* → 6).

```
#keyed = rows came from an object; column _key holds the key each record was
stored under, and is NOT a field of the record
```

## Method

`docs/cold-reads.md`, the reads #1–#4 kind: a fresh reader with **no access to
this repo**, given the rendered document inline and nothing else, told to read it
rather than parse it, to say "not answerable from this document" rather than
guess, and to report what was ambiguous and a confidence score.

The C set as usual, plus one question written for this change:

> **C11.** What was the original top-level shape of the data this document came
> from — a list of records, or something else? Explain how you can tell.

C11 is the trap in the sense read #1 and #3 used the word: an encoding that reads
plausibly as something else. Nothing in the rows says the payload was ever a
dict, and a reader that answers "a list of eight records" has taken the table at
face value.

## The score

| Question | | |
|---|---|---|
| C1–C5, C7, C9, C10 | correct | unchanged from read #5 |
| **C8** complete `ethereum` record | **correct** | twelve fields, **no `_key`** |
| **C11** original shape | **correct** | "an object/map, not a list" |

## What it said about `_key`, unprompted

On C8:

> ethereum — stored under key `"ethereum"`; per the legend `_key` is not a field
> of the record itself, so the record is: …

And listed under *what was ambiguous*:

> **C8**: whether `_key: "ethereum"` belongs in "every field it has" is a
> judgment call. The legend explicitly says it is not a field of the record, so I
> excluded it and noted the key separately.

That is the whole finding. The reader **still saw the question as a judgment
call** — the ambiguity read #5 fell into is still there in the data — and the
legend clause is what decided it. Twelve tokens bought a sentence that settles a
call the document was previously leaving to the reader.

It also did something read #5 never got the chance to: it reported the key
*beside* the record instead of discarding it. Nothing asked for that. The clause
says what `_key` is not, and the reader worked out from "the key each record was
stored under" what it therefore is.

On C11 it named both signals — the `#keyed "_key"` line and the legend — and
reconstructed the original shape, `{"bitcoin": {...}, "ethereum": {...}}`,
correctly.

## What it flagged, none of it about the format

- **C9 and C10 do not name a currency.** The payload carries `usd`, `eur` and
  `gbp`; the reader used `usd` and checked that the ranking and the signs are the
  same in all three. A defect in the *questions*, not the document.
- **`24h_change` is not stated to be a percentage.** Read as percent "because
  that is what the field name conventionally means, which is an inference".
  Correct, and correctly labelled as an inference.
- **`eur`/`gbp`/`usd` are typed `num` while the derived columns are `float`.**
  Noticed, treated as a typing detail of the format rather than a distinction in
  the data, which is exactly right.

Nothing in the list is about `#keyed`, the legend, or the table. Reads #1–#5 each
found something the document should have said; this one found only things the
*questions* should have said.

## Confidence: 9/10

The highest of six reads, and the reason given is that the deducted point is for
the currency and percentage assumptions above — not for anything it had to
reconstruct.

## What this does not settle

**Counting.** This payload is eight rows and thirteen columns; the weakness every
read has leaned on barely gets exercised here. `docs/cold-reads.md` keeps it on
the watch list, and read #5's automated kind is where it keeps showing up.

**One reader, one payload, one sample.** The same day's automated sweep
(`docs/cold-reads/2026-09-12-sweep.md`) asked the same C8 of a different reader
in three arms, which is the second observation this fix has rather than the only
one.
