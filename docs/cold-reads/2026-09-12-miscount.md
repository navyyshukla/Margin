# The miscount, isolated — 2026-09-12

**25 readers, five arms, one payload, three questions that decide anything.**
Run to answer the one finding seven cold reads left open and could not explain:
why does the stored arm miscount `comments`, a column that holds no handle?

## The answer, as far as it goes

| arm | document | questions | fetch tool | missed Q5/Q6 |
|---|---|---:|---|---:|
| `compressed` | compressed | 3 | no | **0/5** |
| `stored` | stored, as it ships | 3 | no | **0/5** |
| `stored-bare` | stored, `\@0004` not `\@0004[345t]` | 3 | no | **0/5** |
| `stored-full` | stored, as it ships | 15 | no | **0/5** |
| `stored-fetch` | stored, as it ships | 15 | **yes** | **1/5** |

Three things follow, in descending order of how much the evidence supports them.

**1. The document is not a sufficient cause.** Twenty readers were given
documents that could not fetch — including ten given the exact bytes that failed
in reads #5 and #7 — and not one of them missed. Every one of the twenty also
listed all thirty `comments` values correctly.

**2. Neither is the size of the task.** `stored-full` restored the sweep's whole
fifteen-question set on the same document and still missed nothing. That rules
out "the reader had more to do" on its own.

**3. Every miss in the run was in the arm that could fetch.** One reader of five,
and it is the only reader of twenty-five that got anything wrong. Counting the
three historical observations, **all four misses ever recorded on this question
came from a reader that had a fetch tool.**

## What the fetch arm actually got wrong, which is the point of D1

`D1` — "list the value of the comments column for every entry, in order" — exists
because reads #5 and #7 could see only that a total had moved. The failing reader
returned:

```
truth  0 3 0 1 0 0 1 1 3 3 0 0 3 0 1 1 2 1 0 0 0 1 1 1 3 2 1 1 1 0
given  0 3 0 1 0 0 0 1 3 3 0 0 3 0 1 1 2 1 0 0 0 1 1 1 3 2 1 1 1 0
                     ^
                   row 7: read as 0, the document says 1
```

and from that, 12 zeros and a total of 30 — both exactly what one misread row
produces. **It is a reading failure, not arithmetic.** The reader did not add
badly; it took the wrong value off one row and then counted its own list
correctly. Seven cold reads have called this "counting"; it is not counting.

That distinction is new and it changes what a fix would even look like. You
cannot explain a sum in a legend. You can, in principle, do something about a
reader losing its place in a row.

## What this does NOT establish, stated before anything else is built on it

**1 of 5 is not a rate.** The bar written into `src/measure_miscount.py` before
the run demanded 3 of 5 to call something reproduced, and the fetch arm did not
clear it. The correct sentence is **suspect, not cause** — and the file prints
exactly that rather than rounding a suggestive result up into a finding.

Nor does this run separate the two things "having fetched" could mean: the turns
spent calling the tool, or the ~600 tokens of retrieved issue body that land in
the reader's context and sit between it and the table. Both are live. Telling
them apart needs an arm that puts retrieved content into the context **without**
the reader having asked for it, and that arm is named here and not built.

## The hypothesis this was built on, which was wrong

That `[Nt]` was to blame. In the stored document the handle sits immediately left
of `comments` and carries a number of its own — `...,\@0004[345t],1,...` — so a
reader scanning for the comment count has a stray number adjacent to the one it
wants. The errors fit: totals of 32 and 33 against 31.

`stored-bare` tested it directly and **cleared it.** `[Nt]` was bought at 0.5
points across the sample set for a benefit cold read #4 proved, and the second,
negative effect guessed at here does not show up at all. The entry in
`docs/thresholds.md` stands unchanged, which is the outcome that required no
edit and is worth recording precisely because nothing had to change.

## Two things about the method, since both cost something

**The first design changed two variables at once.** Arms one to three dropped the
fetch tool *and* cut fifteen questions to three. They came back 20/20 clean,
which said nothing, because either change could have been responsible.
`stored-full` and `stored-fetch` were added afterwards to take them apart. That
is the one-variable rule this project states in `measure_store.py` and
`docs/thresholds.md`, broken in the design of the experiment meant to apply it.

**Five readers per arm is a screening experiment, not a study.** It can point at
a cause. It cannot measure the size of one, and nothing here should be quoted as
a rate.

## Where that leaves the eval

`src/eval_model.py`'s stored arm still reports **73/75** and still fails its own
`GRADED_ALLOWED_GAP = 0`. Nothing in this run changes that number, and the run
does not argue for widening the gate — a threshold moved to fit a result it was
built to catch is not a threshold.

What changes is the description. Until today the two misses were "the stored
document is harder to count, and nobody knows why". They are now: *a reader that
has retrieved from the store sometimes misreads a row of the table, and the
document is not what makes it do so.*
